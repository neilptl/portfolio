ML Algorithm Framework

From Data to Decisions and Creation

Download the guide ↓
Quick-reference guide

A concise comparison of methods across tabular data, computer vision, natural language processing, and generative AI. Start with the source of the training signal, not just the name of the model.

Open the original PDF ↗Download the PNG ↓

Introduction

Machine learning methods differ in how they learn, what they produce, and the kinds of data they use. This visual reference helps beginning AI/ML practitioners and project stakeholders connect those distinctions to practical problems.

Description

The downloadable framework compares 12 algorithms and model families: linear regression, decision trees, random forests, gradient boosting, support vector machines, convolutional neural networks, K-means, principal component analysis, BERT-style transformers, GPT-style transformers, generative adversarial networks, and diffusion models. Each entry includes a learning type, relevant application domains, a short mechanism, an illustrative real-world use case, and a distinguishing feature.

The vector PDF preserves sharp text when enlarged or printed; the high-resolution PNG supports image-based display. Deliverables: ML-Algorithm-Framework.pdf and ML-Algorithm-Framework.png.

Objective

Explain how major machine learning approaches relate to one another across tabular data, computer vision, natural language processing, and generative AI, and support an informed first discussion about method selection.

Process

  1. Reviewed the assignment, the 75-point rubric, and the professional portfolio requirements.
  2. Selected a representative set spanning predictive methods, structure discovery, text understanding, and content generation. The assignment uses “algorithms” broadly; the framework includes both classical algorithms and neural model families.
  3. Classified each entry by its illustrated training signal. Known external targets indicate supervised learning; clustering, projection, and unconditional distribution learning indicate unsupervised learning; targets created from text indicate self-supervised pretraining. Because the assignment asks for supervised/unsupervised categories, the legend explains that self-supervised pretraining is commonly placed within the broader unsupervised category.
  4. Assigned domains based on the input and output in each example rather than treating domains as exclusive categories. SVM spans text, image features, and tabular vectors; GPT spans NLP and generative AI. The listed domains are representative, not exhaustive.
  5. Checked mechanisms and classification against technical documentation and original papers. Specified the training stage for BERT and GPT and the unconditional setup for GANs and diffusion models to avoid assigning an architecture one permanent learning type.
  6. Organized six supervised entries first, followed by structure discovery and language representation, then a final row focused on generative AI. Added direct comparisons between single trees and ensembles, BERT and GPT, and prediction and generation. Used consistent card fields and explicit labels so color is not the only classification cue.
  7. Generated a vector PDF and a high-resolution image, then checked the rendered layout for readability, alignment, and completeness.

Tools and technologies used

ChatGPT/Codex assisted with research synthesis, wording, layout, and production. Python and ReportLab generated the PDF; Poppler rendered the image and supported visual checks. Technical sources included scikit-learn, PyTorch documentation, and original research papers.

This artifact is a conceptual reference; it does not report trained models, datasets, experiments, or measured results.

Value proposition

The framework connects learning signal, mechanism, domain, and use case in one view, helping readers compare prediction, structure discovery, and generation before investigating implementation details.

Unique value

It makes training-stage distinctions explicit and gives generative AI a dedicated comparison row, helping readers avoid equating all transformers with generation or all neural networks with supervised learning.

Relevance

Students can use it to review foundational concepts. Project teams can use it to discuss whether their goal is prediction, structure discovery, or generation before choosing a candidate method. The artifact demonstrates technical communication, source-based synthesis, classification reasoning, and visual organization.

Actual model selection also requires validation against available data, business goals, error costs, interpretability needs, and computing constraints.

How to use the guide

Read the learning-signal legend, find the relevant task and domain, then compare the mechanism and distinguishing feature of candidate methods. Use the numbered references to investigate further. Examples illustrate plausible applications; they are not claims about a particular deployed system or guaranteed performance.

Inside a Neural Network

Six components, one learning loop, and evidence from TensorFlow Playground

View the slides ↗
Visual presentation · 12 slides

An illustrated walkthrough of how a neural network turns inputs into predictions and learns from its mistakes. Each component is defined, drawn, and tied to an experiment I ran in TensorFlow Playground.

Open the presentation ↗Download the PDF ↓

Introduction

Neural networks power image recognition, language tools, and prediction systems, but their inner workings are often explained with equations alone. This presentation is for students and non-specialist colleagues who want a clear mental model of what each part of a network does and why it matters.

Description

The 12-slide deck opens with an architecture diagram that shows data flowing from the input layer through two hidden layers to the output, then into the loss function and back to the optimizer. Six slides follow, one per component: layers, neurons, weights and biases, activation functions, loss functions, and optimization algorithms. Each pairs a definition with a diagram or chart and an observation from TensorFlow Playground. The deck closes with a table that classifies each component as learned or chosen, a page of experiment results, a summary slide, and sources.

Deliverables: the web presentation, with a full-screen present mode, and a 12-page PDF.

Objective

Define and illustrate the six core components of a neural network, show how they work together during training, and use hands-on experiments to show how changing each one affects training speed, model complexity, and performance.

Process

  1. Reviewed the assignment, the 75-point rubric, and the portfolio requirements.
  2. Ran 12 network configurations in TensorFlow Playground on the circle and spiral datasets, changing one setting at a time: hidden layers, neurons, activation function, learning rate, input features, and noise. I held the seed (0.42), 50% train/test split, and batch size (10) constant.
  3. Repeated most configurations 3–5 times and recorded the median test loss, because random starting weights changed the results from run to run.
  4. Designed one architecture diagram with numbered badges, so every component slide connects back to its place in the network.
  5. Wrote each component slide as a definition, a visual, and an “observed” callout with Playground evidence. Charts of the activation, loss, and gradient-descent curves are computed from the actual functions.
  6. Added a learned-versus-chosen classification table to separate parameters from design decisions, then a summary of why visualization matters.
  7. Built the slides in HTML and SVG, exported a PDF, and checked every slide for alignment, overflow, and readability. Images include descriptive alt text.

Tools and technologies used

TensorFlow Playground for experiments. HTML, CSS, and JavaScript with inline SVG for the slides, diagrams, and charts. Google Chrome to export the PDF, and Python with Pillow to crop the Playground screenshots. Claude Code (Anthropic) assisted with running and recording the experiments, drafting, and building the slides.

Value proposition

The presentation turns abstract vocabulary into a picture someone can reason with. A reader can find any component on the architecture diagram, see what it does, and see what happened when it was changed.

Unique value

Every concept is backed by a measured result rather than a generic claim. The slides report medians across repeated runs, note where results varied, and separate learned parameters from human design choices, a distinction that is often blurred in introductory material.

Relevance

Students can use it to review fundamentals before building models. Teams can use it to explain to stakeholders why a model needs tuning, more data, or a different architecture. It demonstrates experimental reasoning, technical communication, and visual design, complementing the method-selection focus of the ML Algorithm Framework.

How to use the presentation

Start with slide 2 for the big picture, then read the component slides in order or jump to the one you need. Select Present for full-screen slides and use the arrow keys to move. To reproduce an experiment, open the Playground and apply the settings listed on slide 10.

What It Takes to Train an LLM

Eight stages, four resources, and six real models

View the infographic ↗
Infographic · 1 slide + explanatory document

Training a large language model is a chain of stages, and each one draws on data, compute, energy, and people differently. This slide shows where those resources go and what is publicly known about GPT, Gemini, Llama, Claude, and DeepSeek models.

Open the infographic ↗Download the PDF ↓Download the PNG ↓Read the explanatory document ↗

Introduction

Announcements about large language models often quote one dramatic cost, which hides where the money goes and what the figure leaves out. This infographic is for students, project stakeholders, and anyone weighing an AI investment who wants a realistic picture of what training involves.

Description

A single 16:9 slide follows eight stages: collect, clean, design, pretrain, evaluate, fine-tune, safety test, and deploy. A matrix under the stages rates how heavily each uses data, compute, energy, and people and time. Below it, a panel gives each resource’s share of development cost and role in performance, and a table compares GPT-3, GPT-4, Gemini 1.0 Ultra, Llama 3.1 405B, Claude 3.5 Sonnet, and DeepSeek-V3.

Deliverables: the web version, a PDF, a PNG, and an explanatory document (PDF) covering the main points, key considerations, and design rationale.

Objective

Illustrate the key steps from data collection to deployment, explain how data, compute, energy, and time contribute to model performance and cost, and communicate infrastructure information clearly to varied audiences.

Process

  1. Reviewed the assignment and course resources from IBM Technology, Eye on Tech, and Stephen Wolfram.
  2. Traced each figure to a primary paper, model card, or report wherever one was available, and noted the few that rely on secondary reporting.
  3. Separated cloud-rental estimates, amortized estimates, and developer statements, because mixing them would make unlike numbers look comparable.
  4. Marked undisclosed values as “Not disclosed” and labeled my own derivations and qualitative ratings.
  5. Designed a matrix that joins the process view to the resource view, then placed log-scale cost markers inside the model table.
  6. Built the slide in HTML and CSS, checked the chart colors for color-vision deficiency, and reviewed the rendered slide for overflow and legibility.

Tools and technologies used

HTML, CSS, and JavaScript for the slide and document. Google Chrome to export the PDF and PNG files. Claude Code (Anthropic) assisted with research, drafting, and building the slide.

Value proposition

The slide lets a reader see in one view which stages consume which resources, which costs dominate, and how far to trust a published number.

Unique value

Most cost graphics present one number per model. This one shows competing estimates side by side, names the method behind each, and states plainly what developers have not disclosed.

Relevance

Teams can use it to frame build-versus-buy discussions and to question headline training costs. It demonstrates infrastructure and cost analysis, source evaluation, and information design, a different skill set from the method comparison in Artifact 01 and the experiments in Artifact 02.

How to use the infographic

Read the arrows left to right, then the bars beneath them to see what each stage consumes. Use the resource panel for cost shares and the model table for specific examples. Compare costs by marker type, since the methods differ.
